How the data reaches the dashboards

Both BRs follow Kafka → Spark → ClickHouse → Grafana. Reference data is loaded in batch; events stream through Kafka into Spark Structured Streaming, which writes serving tables to ClickHouse that the Grafana dashboards query directly.

Spark shrinks about 49 million trips into 146 thousand zone-hours; ClickHouse stores the serving tables at roughly 5x compression, which is why every dashboard query answers in milliseconds.

How it runs

  • make demo-br BR=1,2 runs scripts/start.py: Docker Compose up, Kafka topics reset, ClickHouse DDL, spark-submit per BR on the Spark 4.0 standalone cluster (1 worker, 2 cores; 1 core and 512 MB per job), wait until each stream is ready, then start the producers.
  • Grafana reads ClickHouse with the grafana-clickhouse-datasource plugin and Spark metrics from Prometheus.
  • Benchmarks: make br1-bench and make br2-bench run the same jobs in benchmark mode and write timings to tour.job_run / pricing.job_run.

BR1 Tour route: naive vs optimized

Both modes solve the same 20,000 tour requests (4-8 stops, 3 cities). Naive uses a Python row UDF, a shuffle join with the distance-matrix parquet, and AQE off with 200 shuffle partitions. Optimized uses mapInPandas with numpy, broadcast coordinates and joins, AQE on and Arrow transfer. The benchmark never touches tour.fact_tour / tour.fact_tour_leg (the tours the Tour finder reads). Its timed sink_clickhouse stage truncates and reloads tour.dim_landmark and tour.dist_matrix with identical data, so for about 18 s per repetition the landmark lookups and map can be empty - run it when nobody is using the dashboards. The headline speedup is the median of the per-rep speedups, 16.75x (range 16.62-16.99x). Medians of 3 repetitions, nothing else on the Spark cluster.

Findings

  • Correctness. Naive and optimized outputs were compared row by row from the lake. 20,000 tours in both; total_cost_vnd is equal on all 20,000 (sum 9,444,273,402 VND in both); total_km differs by at most 9e-13.
  • Isolation matters. Two same-day runs while BR2 shared the 2-core worker gave naive 79.5 s and 72.2 s, optimized 3.35 s and 5.20 s (speedups 23.8x and 13.9x). Isolated runs give 16.6-17.0x.
  • Next target: the ClickHouse sink. Writing to ClickHouse (18.1 s) takes about 6 times the whole optimized compute (3.06 s). Candidates: the repo's parallel write_partitions writer, or native-format inserts.

BR2 Dynamic pricing: raw files vs partitioned lake

The capacity baseline covers 12 months (2025-07 to 2026-06), 16 landmark zones, and the P95 of hourly bookings per zone, day type and hour. It is computed either from the raw monthly TLC parquet files or from the normalized lake, partitioned by service and pickup_month. The order alternates raw,lake / lake,raw / raw,lake to limit page-cache bias. Medians of 3 repetitions. The benchmark writes pricing.job_run and does not touch serving data. --bench-lake-build rewrites the lake partitions (same data), so do not run it while the replay producer is reading.

Correctness, storage and cost

  • Correctness. Identical in all 6 runs: hourly aggregate 134,462 zone-hours and 9,305,304 bookings; capacity 768 slots, checksum 75,940.
  • Storage. Raw 873 MB in 13 files. Lake 460 MB in 26 parquet files (53% of raw).
  • Break-even. One-off lake build (rep 1): 44.53 s for 48,950,921 trip rows (13 months). If the lake were built only for this, it pays back after 44.53 / (14.08 − 7.42) = about 7 rebuilds.
  • Pipeline nuance. In the real pipeline the baseline writes this lake anyway, because the replay producer reads it. The lake is not an extra cost there.

Streaming observations

From the live demo. This is not a controlled benchmark.

  • BR1: peak 2,743 requests/s; average micro-batch latency 399 ms.
  • BR2: average input 1,496 rows/s (producer-bound) against a processing capacity of 21,627 rows/s, about 14x headroom; average batch latency 530 ms. The July 2026 replay produced 11,534 zone-hour rows on top of 134,462 history rows.

Product-owner walkthrough

Eight questions a product owner can answer in the dashboards. Dashboards: BR1 Tour finder and BR2 Pricing advisor. Each starts with an "Ask the data" panel of one-click example questions.

Q1. What is the cheapest tour in each city?

HCMC: 6,725 tours, cheapest 99,530 VND, median 596,542. Hanoi: 6,743 tours, 79,273 / 368,453. Da Nang: 6,532 tours, 83,635 / 431,880. Cheapest by stops (4, 5, 6, 7, 8): HCMC 99,530 / 119,136 / 201,101 / 205,458 / 351,591; Hanoi 79,273 / 118,053 / 157,759 / 217,110 / 221,117; Da Nang 90,179 / 83,635 / 153,035 / 174,956 / 235,120.

Insight: Hanoi has the lowest entry price and the lowest median. Price rises with stops in every city, except that Da Nang 5 stops (83,635) is cheaper than 4 stops (90,179).

Q2. Budget traveller: Hanoi, 5 stops, at most 500,000 VND

1,316 options. Cheapest 118,053 VND (tour 2026: Đình Đồng Nhân → Đình Tú Thị → Đền Bạch Mã → Đền Quan Đế → Đình làng Ái Mộ). Median 314,336 VND. Shortest 3.11 km.

Insight: a filter on budget and stops gives a short list the app can show at once, from 1,316 matching tours.

Q3. Must-see: Miếu Ngũ Hành (HCMC)

244 tours include it. The cheapest costs 160,273 VND (tour 16128).

Insight: a must-see stop can be turned into a fixed-price offer starting from the cheapest tour that includes it.

Q5. Default pricing rule (surge at 80% of capacity, raise 15%)

2025-07 to 2026-07: 32,462 surge zone-hours, 22.2% of 145,996 hours. Extra fare revenue $12,766,917, assuming demand holds. Average demand ratio 61.7%.

Insight: about one hour in five is in surge under the default rule. The revenue figure is an upper bound because it assumes no demand loss.

Q6. Weekend rule on history (surge at 60%, raise 25%)

Weekends, history only: 20,775 of 38,752 hours surge (53.6%). Extra fare revenue +$10,293,093.

Insight: a lower threshold and a higher raise put more than half of the weekend hours in surge. Test it on demand loss before use.

Methodology and threats to validity

  • 3 repetitions on one laptop; medians with min-max.
  • OS page cache can favour later runs. BR2 alternates the variant order to reduce this.
  • BR1 "total" excludes the optimized warm-up stages (landmarks, dist_matrix, sink_clickhouse).
  • p95 comes from 10 samples per query.
  • Streaming figures come from the live demo, not a controlled run.
  • The revenue what-if assumes no demand loss after a price rise.
  • Benchmarks ran with nothing else on the Spark cluster. BR1 results change when other work shares the worker.
