1. Business requirement

Hỗ trợ định giá linh hoạt thời gian thực (Dynamic Pricing Insights)

A taxi and ride business near New York City's tourist landmarks wants to know, hour by hour, whether demand at each landmark is close to its practical capacity. For every landmark and hour, the platform computes a demand ratio (active bookings compared with capacity) and turns it into an automatic price suggestion. When the demand ratio exceeds 80% of capacity, the suggestion is a 15% fare increase: "Nhu cầu > 80%: Gợi ý tăng giá 15%". Otherwise the suggestion is "Giữ giá" (hold price). The output is stored in ClickHouse and charted in Grafana and Looker Studio.

What the business gets

  • Hourly demand ratio per landmark.
  • Current price suggestion per landmark.
  • Count of landmarks in surge.
  • Heatmap of landmark × hour.

2. How it works in one paragraph

The pipeline first builds a historical baseline from 12 months of NYC yellow taxi trips (2025-07 to 2026-06). From that baseline it derives a capacity for each landmark, split by weekday or weekend and by hour of day. Then one completed month (2026-07) is replayed through Kafka to simulate a live feed. Spark Structured Streaming counts drop-offs per landmark per hour, divides each count by that landmark's capacity, and writes the ratio and the price suggestion to ClickHouse every 10 seconds. Dashboards in Grafana and Looker Studio read from ClickHouse.

3. Data flow

1. scripts/download_tlc.sh Downloads monthly NYC TLC yellow taxi parquet (~3-4M trips/month) plus taxi_zone_lookup.csv into data/br2/raw/.
↓
2. jobs/br2_dynamic_pricing/job.py (baseline) Builds the fact_trips lake table, computes capacity per (location_id, day_type, hour_of_day), and inserts baseline demand ratios into ClickHouse with source='batch'. Runs once; skipped when data/br2/lake/dim_capacity exists.
↓
3. ingestion/producers/produce_br2.py Reads the replay month (BR2_REPLAY_MONTH) from fact_trips via pyarrow, sorts by pickup_datetime, and publishes JSON to Kafka topic tlc.trips.
↓
4. Kafka topic tlc.trips Simulated live feed.
↓
5. jobs/br2_dynamic_pricing/job.py (streaming) Spark Structured Streaming: 1-hour tumbling window per landmark, joins capacity, computes ratio and price action, 10-second trigger, update mode.
↓
6. ClickHouse pricing.demand_ratio_hourly ReplacingMergeTree(updated_at), ORDER BY (location_id, window_start); views v_demand_ratio and v_latest_suggestion.
↓
7. Grafana http://localhost:3000/d/br2-pricing Local dashboard.
↓
8. Looker Studio via bore.pub tunnel to ClickHouse MySQL port 9004 External dashboard.

Active bookings
Count of trips whose drop-off location (do_location_id) is the landmark, grouped by pickup hour (window_start). Note: this is drop-off, not pickup.
day_type
weekend if the day is Saturday or Sunday, otherwise weekday.
Capacity
Approximate 95th percentile (Spark percentile_approx(0.95), cast to int) of hourly active bookings per (location_id, day_type, hour_of_day), over the baseline 2025-07 to 2026-06. Hours with zero bookings are absent from the grouping, so capacity skews high for quiet zones.
Demand ratio %
active_bookings × 100 / capacity when capacity > 0, otherwise NULL. Landmark-hours with no baseline capacity get a NULL ratio and hold price.
Price action
A strict ratio above 80 gives "Nhu cầu > 80%: Gợi ý tăng giá 15%" and suggested_fare = avg_fare × 1.15. Otherwise the action is "Giữ giá" and suggested_fare = avg_fare. Constants: SURGE_THRESHOLD_PCT = 80, SURGE_UPLIFT = 0.15.
Timestamps
NYC local wall-clock time. The Spark session timezone is kept at UTC so that hour boundaries are not shifted.

8. Runbook

Step 0: Prerequisites

  • Docker Desktop running.
  • Git repo cloned and working directory is the repo root.
  • .env created from the template (cp .env.example .env). Set CLICKHOUSE_PASSWORD now; LOOKER_PASSWORD is needed for Dashboards (section 9).
  • Linux only: after the download, run chmod -R a+rwX data so the Spark container (uid 1001) can write.

Step 1: Download NYC TLC data

Downloads about 13 monthly yellow taxi parquet files (~1 GB) to data/br2/raw/yellow/, plus data/br2/raw/taxi_zone_lookup.csv if missing. The pipeline does not download data; this is a manual prerequisite.

bash scripts/download_tlc.sh yellow 2025-07 2026-07

Step 2: Run the pipeline

make demo-br BR=2

scripts/start.py runs these steps in order:

  1. Infra: builds the spark-local image and starts clickhouse, kafka, tour-map, spark-local, grafana, prometheus, spark-master and spark-worker. Waits for the ClickHouse and Kafka healthchecks.
  2. Topics: scripts/topics.py --reset recreates the Kafka topics, including tlc.trips.
  3. Schema: applies sql/clickhouse/ddl_br2.sql (database pricing, table pricing.demand_ratio_hourly, views v_demand_ratio and v_latest_suggestion).
  4. Spark job: submits jobs/br2_dynamic_pricing/job.py from the spark-local container to the Spark cluster (driver and executor 512m, spark.cores.max=1, spark.sql.shuffle.partitions=4). On the first run, or whenever data/br2/lake/dim_capacity is missing, the job builds the baseline from the raw parquet first, then starts the streaming query. start.py waits up to SPARK_READY_TIMEOUT (default 180 s) for the streaming query to start.
  5. Producer: starts ingestion/producers/produce_br2.py, which replays the BR2_REPLAY_MONTH lake month to tlc.trips.

Logs: logs/demo/br2-spark.log and logs/demo/br2-producer.log. Ctrl+C in that terminal stops the Spark job and the producer.

Every run resets tlc.trips but not the Spark checkpoint, so delete data/br2/checkpoints before rerunning (see Reset and replay again below).

First run: the baseline finishes before the streaming query starts, so it can exceed the 180 s readiness wait. Use SPARK_READY_TIMEOUT=1800 make demo-br BR=2.

Step 3: Check results in ClickHouse

Connect with the client, then run the two queries below.

docker exec -i clickhouse clickhouse-client --password "${CLICKHOUSE_PASSWORD:-clickhouse}" --multiquery

Query 1: row counts and demand distribution. Expected: about 8000 baseline hours plus growing stream hours. Surge hours are typically about 10–20%.

SELECT
  source,
  COUNT(*) as n_rows,
  uniq(location_id) as n_zones,
  min(window_start) as earliest_hour,
  max(window_start) as latest_hour,
  countIf(demand_ratio_pct > 80) as n_surge_hours
FROM pricing.v_demand_ratio
GROUP BY source
ORDER BY source DESC;

Query 2: latest suggestions. Expected: the latest window_start per landmark, with price_action and suggested_fare.

SELECT * FROM pricing.v_latest_suggestion ORDER BY demand_ratio_pct DESC;

Step 4: Monitoring UIs

  • Spark Master: http://localhost:8082 (Spark worker metrics via /metrics/prometheus/)
  • Kafka UI: http://localhost:8080 (browse topic tlc.trips)
  • Grafana: http://localhost:3000 (username admin, password admin)

Reset and replay again

make demo-br BR=2 already resets the Kafka topic tlc.trips. It does not clear the Spark checkpoint or the stream rows in ClickHouse, so clear those before a fresh replay:

# Clear the Spark streaming checkpoint
rm -rf data/br2/checkpoints

# Remove stream-sourced rows from ClickHouse
docker exec clickhouse clickhouse-client --password "${CLICKHOUSE_PASSWORD:-clickhouse}" -q "ALTER TABLE pricing.demand_ratio_hourly DELETE WHERE source = 'stream'"

# Rerun: resets tlc.trips, reapplies the DDL, restarts streaming and the replay
make demo-br BR=2

To rebuild the baseline as well, also delete data/br2/lake/dim_capacity before rerunning. The next run recomputes the baseline and re-inserts the source='batch' rows; demand_ratio_hourly is a ReplacingMergeTree, so duplicates collapse on merge.

9. Dashboards

Local dashboard (Grafana)

Open http://localhost:3000/d/br2-pricing (credentials admin:admin). The dashboard has a fixed time range of July 2026, which matches the stream data. To see the baseline too, set the date range to 2025-07-01 to 2026-07-31. No tunnel is needed because Grafana queries ClickHouse inside the data-net Docker network.

Panels:

  1. Demand ratio % by landmark: time series of hourly demand ratios per landmark, with a red threshold at 80% surge.
  2. Current suggestion per landmark: table of latest suggestions with demand ratio, suggested fare, and price action.
  3. Landmarks above 80% now: stat card with the count of zones currently in surge.
  4. Surge hours by landmark in range: table of total surge hours per landmark within the selected window.

External dashboard (Looker Studio)

Looker Studio connects through a public bore.pub tunnel to ClickHouse MySQL port 9004. Use the MySQL connector with database pricing and user looker, and add the tables v_demand_ratio and v_latest_suggestion. If the table list fails or the query times out, use a custom query such as SELECT * FROM pricing.v_demand_ratio. Set data freshness to 1 minute, which is the MySQL connector minimum.

Recommended charts:

  1. Time series: X = window_start, Y = demand_ratio_pct, breakdown by landmark, with a reference line at 80.
  2. Heatmap / pivot table: rows = landmark, columns = hour_of_day, values = average demand_ratio_pct.
  3. Table: landmark, demand_ratio_pct, avg_fare, suggested_fare, price_action. Conditional formatting: red cell background where demand_ratio_pct > 80.
  4. Scorecard: single value = count of zones with demand_ratio_pct > 80.
  5. Filters: date range (picker on date) and landmark (dropdown).

Security warning

The public tunnel (bore.pub) exposes ClickHouse's MySQL port (9004) to the internet. By default the default user has password clickhouse, which is public in this repo. Before starting the tunnel:

  1. Set strong passwords in .env (CLICKHOUSE_PASSWORD and LOOKER_PASSWORD, at least 32 random characters each).
  2. Create a read-only looker user with GRANT SELECT ON pricing.*.
  3. Stop the tunnel after your demo: docker compose --profile tunnel stop tunnel.

Tunnel setup (reference)

cp .env.example .env
# Edit .env and set strong values

docker exec clickhouse clickhouse-client --password "$CLICKHOUSE_PASSWORD" --multiquery -q "CREATE USER IF NOT EXISTS looker IDENTIFIED WITH double_sha1_password BY '$LOOKER_PASSWORD'; GRANT SELECT ON pricing.* TO looker"

docker compose --profile tunnel up -d tunnel
docker logs tunnel   # look for: listening on... <tunnel-id>.bore.pub:<port>

Fallback tunnels if bore.pub is down (no SLA): Pinggy (ssh -p 443 -R0:localhost:9004 tcp@a.pinggy.io, 60-minute sessions) or ngrok (ngrok tcp 9004, card verification required for TCP on the free plan).

10. Assumptions and limitations

  • Capacity is derived (P95), not ground truth. No public per-zone active vehicle count exists. The baseline months 2025-07 to 2026-06 establish a "practical capacity" from historical traffic. Hours with zero bookings are excluded, so very quiet zones' capacity may be slightly overestimated.
  • "Real-time" is a replay. The pipeline re-publishes one completed calendar month to Kafka in order, simulating a live feed. True live data would require a connection to TLC's real-time API, which is not public at this scale.
  • Looker freshness is at least 1 minute. The MySQL connector's minimum data freshness is 1 minute. Micro-batches arrive every 10 seconds, but charts update at most every minute.
  • Public tunnel (bore.pub) has no SLA. The free service may go down; fall back to Pinggy or ngrok if needed.
  • bitnamilegacy images receive no security updates. bitnami/spark was removed from Docker Hub in September 2025. The archived bitnamilegacy versions are stable but no longer patched. For production, migrate to a maintained Spark image and keep the Kafka connector matched to its Spark and Scala versions.
  • BR2 (batch demand forecast) and the rooms variant are out of scope. BR2 covers taxi trips only. A multi-modal version (rooms, other services) would require extending LANDMARKS and adding data sources.
